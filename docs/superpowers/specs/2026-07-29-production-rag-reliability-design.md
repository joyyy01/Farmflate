# Farmflate 운영형 RAG 신뢰성 설계

## 목적

Farmflate의 밭 분석·위험 안내 질문에 대해, 승인된 농업 근거만 사용하고 출처를 읽기 좋게 제시하며, 문서가 늘어난 뒤에도 품질·보안·지연시간을 같은 조건에서 검증할 수 있게 한다. 이 설계는 기능 수를 늘리기 위한 것이 아니라 현재 RAG가 포트폴리오와 실무 검토에서 설명 가능한 운영 경계를 갖추게 하는 것이다.

## 조사 근거

- OpenAI의 평가 가이드는 과업·테스트 입력·판정 기준을 분리해 실행하고, 결과를 분석해 반복 개선하는 흐름을 권장한다. 따라서 평가 세트와 코퍼스가 바뀐 결과를 평균 내지 않는다.
- pgvector는 HNSW가 정확 검색 대비 재현율·메모리·속도 트레이드오프를 가진다고 설명한다. 현재 45개 실버 평가에서 hybrid가 FTS보다 이득이 없었으므로, 지표 없이 HNSW/RRF를 기본 경로로 켜지 않는다.
- OWASP는 RAG가 간접 프롬프트 인젝션을 완전히 막지 못한다고 명시한다. 따라서 검색 문서는 명령이 아닌 비신뢰 데이터로 표시하고, 모델의 도구 권한과 출력 인용을 코드에서 제한한다.

## 현재 관찰과 문제

1. 농사로 수집기는 최신 1건만 활성화한다. 같은 출처에 여러 주차 문서를 동시에 보관할 수 없어, 실제 다문서 검색과 혼합 질의의 품질을 측정할 수 없다.
2. 검색 결과의 청크별 인용을 그대로 화면 계약에 전달한다. 같은 PDF에서 나온 세 청크가 사용자에게 세 개의 같은 출처로 표시된다.
3. `AUTO_GENERATED` 실버 평가가 있지만, 평가 실행이 현재 코퍼스 스냅샷과 일치하는지는 보장하지 않는다. 현재 `PASSED`는 모든 반환 청크가 정답 근거여야 해 top-k 검색의 통과 여부로는 지나치게 엄격하다.
4. 승인된 문서라 해도 본문 안의 지시문은 비신뢰 입력이다. 현재 시스템 프롬프트와 읽기 전용 도구 제한은 있지만, 악성 문서가 검색된 상황을 재현하는 테스트와 명시적인 경계 표기가 없다.

## 대안 비교

### A. 검증 가능한 PostgreSQL RAG 강화 — 채택

PostgreSQL을 지식·평가·감사 시스템의 단일 저장소로 유지한다. 다문서 수집, 코퍼스 지문, 순위 지표, 비신뢰 근거 경계, 출처 집계를 추가한다. 현재 Spring/Python 분리와 승인·반출 경계를 보존하며 외부 벡터 DB나 관리형 RAG를 추가하지 않는다.

장점은 현재 프로젝트의 데이터 소유권·Flyway·감사 구조와 맞고, 구현·측정 근거를 코드와 DB에서 재현할 수 있다는 점이다. 단점은 임베딩 제공자 호출 지연이 남으므로 hybrid는 평가 통과 전까지 비활성이다.

### B. HNSW 파라미터와 RRF 가중치부터 튜닝 — 기각

현재 코퍼스는 문서 1건에서 출발해 의미 검색의 이득을 검증할 표본이 부족하다. pgvector 파라미터를 조정해 일시적인 점수를 만드는 것은 근거가 약하고, 외부 임베딩 지연도 해결하지 못한다. 다문서 평가가 쌓인 뒤 후보로 남긴다.

### C. Bedrock Knowledge Base 또는 외부 벡터 DB로 교체 — 기각

관리 기능은 얻지만 데이터 이동·권한·비용·관측 경계가 늘어난다. 현재 문제는 저장소 부족이 아니라 코퍼스·평가·보안 경계 부족이므로, PostgreSQL에서 검증한 뒤 실제 운영 규모가 확인될 때 재검토한다.

## 선택한 설계

### 1. 문서 식별자와 다문서 코퍼스

- `rag.document.external_id`를 개별 발행물의 안정 식별자로 사용한다. 한 출처 아래 여러 발행물은 동시에 `CURRENT`일 수 있다.
- 재수집은 동일 `(source_id, external_id)`의 이전 현재 문서만 supersede한다. 다른 주차·다른 공문은 검색 가능 상태를 유지한다.
- 농사로 수집기는 `--weeks 1..12`를 지원한다. 각 PDF는 `cntntsNo` 기반 `external_id`와 발행일 기반 `source_version`으로 적재한다.
- 기존에 `external_id`가 비어 있는 문서는 `source_version`으로 보정하고, 부분 고유 인덱스로 출처별 발행물의 현재 스냅샷을 하나로 제한한다.

### 2. 비신뢰 검색 근거 경계

- 검색 도구는 근거마다 `citationId`, 발행 출처, 본문, `untrusted=true`를 포함한 구조화된 데이터만 모델에 전달한다.
- 제어 문자·제로폭 문자는 제거하고, 시스템 지시·도구 호출·비밀 요구 형태의 문구를 탐지한다. 탐지된 청크는 모델 문맥과 인용 후보에서 제외하며 trace에 개수만 남긴다.
- 시스템 지시는 검색 본문이 명령이 아니며, 도구 호출·권한 변경·비밀 요청의 근거가 될 수 없음을 명확히 한다.
- 이 조치는 완전한 방어를 주장하지 않는다. 읽기 전용 도구 허용 목록, 출처 승인, 인용 일치 검증, 입력 크기 제한과 함께 쓰는 방어 심층화다.

### 3. 출처 표현과 답변 계약

- 내부적으로는 청크 단위 `citationId`를 계속 사용해 답변 근거를 검증한다.
- 외부 응답에서는 `(title, sourceUrl)` 기준으로 같은 출처를 하나로 합치고, 몇 개 청크가 근거인지 `evidenceCount`를 함께 반환한다.
- 답변이 근거와 연결되지 않으면 기존과 같이 `needs_context`를 반환한다. 출처 집계는 근거 검증을 완화하지 않는다.

### 4. 평가 스냅샷과 순위 지표

- 평가 시작 시 활성 케이스가 기대하는 현재 청크의 ID·본문 해시를 정렬해 SHA-256 코퍼스 지문을 만든다. 실행 행에 저장하고, 기대 청크가 더 이상 현재 문서가 아니면 평가를 시작하지 않는다.
- `eval_result`에 `reciprocal_rank`와 `first_relevant_rank`를 저장한다. `recall@k`와 `precision@k`는 유지한다.
- `PASSED`는 적어도 하나의 기대 근거를 찾았는지로 한정한다. 전체 top-k가 모두 정답 근거인지 여부는 통과 상태가 아니라 `precision@k` 지표로 해석한다.
- 비교기는 같은 데이터셋·버전뿐 아니라 같은 코퍼스 지문만 비교한다. 자동 실버와 사람 검토 골드의 origin도 같아야 한다.

### 5. 검증 범위

- 단위 테스트: 다문서 supersede 경계, 악성 검색 본문 제외, 출처 집계, 평가 지문 불일치, MRR 계산.
- 통합 검증: 농사로 공식 API에서 여러 주차 PDF를 적재하고 lexical/hybrid를 같은 코퍼스 지문·동일 실버 세트에서 비교한다.
- API 검증: 내부 인증을 포함한 chat 요청에서 중복 출처 없이 `grounded` 또는 `needs_context` 계약을 확인한다.

## 비목표

- hybrid를 자동으로 활성화하지 않는다.
- 사람 검토를 자동 실버 세트로 대체해 실제 사용자 만족도를 주장하지 않는다.
- 외부 MCP 서버, 외부 벡터 DB, 무제한 자율 행동 도구를 추가하지 않는다.
- 의료·농약 처방을 확정적으로 생성하지 않는다. 현재 근거가 부족하면 `needs_context`를 유지한다.

## 완료 기준

1. 하나의 승인 농사로 출처에서 최소 3개 현재 발행물을 동시에 검색할 수 있다.
2. 동일 발행물을 재수집해도 중복 문서가 생기지 않고, 해당 발행물만 갱신된다.
3. 악성 지시문이 포함된 검색 청크는 모델 컨텍스트·인용 목록에 전달되지 않는다.
4. API 응답은 같은 PDF의 여러 청크를 한 출처로 보이고 근거 청크 수를 제공한다.
5. 서로 다른 코퍼스 지문의 평가 실행은 비교가 거부되며, MRR·재현율·precision@k·p95가 실행 이력에 남는다.
6. Python 전체 테스트와 Spring 테스트, 실제 공식 API 적재·채팅 smoke 검증이 통과한다.
