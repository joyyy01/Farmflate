# ADR-003: 하이브리드 검색은 측정 결과로만 활성화한다

- 상태: 채택
- 결정일: 2026-07-29

## 문제

하이브리드 RAG는 키워드가 정확히 일치하는 짧은 문서 집합에서는 FTS보다 좋아지지 않을 수 있다. 벡터 호출과 HNSW 검색은 비용과 지연 시간을 추가한다. “벡터 검색을 도입했다”는 사실만으로 품질 개선을 주장하면 안 된다.

## 결정

- `RAG_HYBRID_ENABLED`의 기본값은 `false`다.
- `rag.eval_case`의 기대 청크·기대 인용을 기준으로 lexical과 hybrid 결과를 각각 측정한다.
- `python -m app.rag.metrics_cli --days 30`으로 경로별 평가 건수, 평균 recall@k, 평균 citation precision, 요청 수, p50/p95 지연 시간을 확인한다.
- 다음 기준을 모두 충족할 때만 해당 환경에서 hybrid를 활성화한다.
  1. 실제 사용자 의도를 대표하는 활성 평가 케이스가 최소 20개 이상이다.
  2. hybrid의 평균 recall@k가 lexical보다 0.05 이상 높다.
  3. citation precision이 lexical보다 낮아지지 않는다.
  4. p95 검색 지연 시간이 현재 lexical 기준의 1.2배를 넘지 않거나, 제품의 Agent 도구 시간 제한 안에 있다.

## 기준의 근거

- 20개 미만의 작은 표본은 일부 문서나 표현 변화에 지나치게 좌우되므로 기능 기본값을 바꿀 근거로 부족하다.
- 0.05는 미세한 반올림 차이보다 실제 검색 후보 변화가 있었다고 판단할 최소 개선 폭이다. 이는 성능 결과가 아니라 의사결정 임계값이다.
- recall만 높고 인용 정확도가 낮으면 모델에 불필요한 문맥이 더 많이 전달돼 답변 신뢰도가 오히려 나빠질 수 있다.
- p95는 평균보다 드문 느린 요청을 드러내므로, 사용자 체감과 Agent 도구 타임아웃을 함께 관리할 수 있다.

## 포트폴리오에 쓸 수 있는 사실의 경계

- 측정 전: “PostgreSQL FTS·pgvector RRF와 평가/추적 구조를 구현했고, 수치 기준으로 활성화를 제어했다.”
- 측정 후: 명령 출력과 기간, 케이스 수를 함께 보관한 경우에만 “recall@k가 X에서 Y로 개선됐다”처럼 수치를 쓴다.
- 쓰면 안 되는 표현: 데이터나 평가 케이스 없이 “하이브리드 RAG로 검색 성능을 개선했다.”

## 2026-07-29 로컬 검증 경계

PostgreSQL 18.4에서 pgvector 0.8.5, `vector(1536)`, HNSW 인덱스, 임베딩 적재, RRF hybrid 질의까지는 실제로 검증했다. 다만 이 검증은 파이프라인 연결을 확인하기 위한 임시 문서 1건·질의 1건이며, 결과와 trace는 삭제했다. 따라서 기본값은 계속 `false`이고, 이 결과만으로 성능 개선이나 운영 활성화를 주장하지 않는다.
