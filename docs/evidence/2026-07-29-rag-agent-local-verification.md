# RAG·Agent 로컬 검증 기록 (2026-07-29)

## 왜 검증했는가

RAG·Agent 구현을 포트폴리오에 설명하려면 코드 존재만으로는 부족하다. PostgreSQL 확장, Flyway, 임베딩 적재, RRF 질의, 출처 승인 흐름이 서로 연결되는지를 실제 로컬 환경에서 확인했다.

## 어디서·무엇을 검증했는가

- 환경: Windows 로컬 PostgreSQL 18.4, `interview_db`, Python Agent, Spring Boot backend.
- DB: Flyway V20~V24 적용, pgvector 0.8.5 활성화, `rag.chunk.embedding vector(1536)`, `rag_chunk_embedding_hnsw_idx` 확인.
- 적재: `text-embedding-3-small`로 생성한 임시 문서 1건이 `READY` 상태와 1536차원 벡터로 저장됨을 확인.
- 검색: 동일 임시 질의가 PostgreSQL FTS + pgvector RRF `hybrid` 모드에서 1개 후보를 반환함을 제어된 smoke로 확인했다. 다만 서비스 기본값은 `RAG_HYBRID_ENABLED=false`인 lexical FTS이며, hybrid는 평가 기준을 충족한 뒤에만 명시적으로 켠다.
- 거버넌스: 운영자 CLI로 `PENDING` 등록 후 `APPROVED` 검토를 실행했고, `REGISTERED`·`APPROVED` 감사 이벤트가 기록됨을 확인.
- 공식 출처: 농촌진흥청 농사로 `weekFarmInfoList` API에서 최신 주간농사정보 PDF를 가져와 승인된 출처로 적재했다. 현재 문서 1건·청크 9개가 생성됐고, 한국어 병해충 질의에서 lexical 후보 8개가 반환됐다.

## 무엇을 수정했는가

- 자연어 한국어 질문의 모든 어절을 AND로 묶어 검색 0건이 되는 문제를 발견했다. PostgreSQL `websearch_to_tsquery`를 유지하되 공백 토큰을 OR 후보로 구성해 랭킹 기반 회수율을 확보했다.
- 실제 pgvector 실행에서 RRF SQL의 괄호 누락을 발견해 수정했다. 빈 mock만 통과하는 테스트의 한계를 실제 DB smoke 검증으로 보완했다.
- pgvector 활성화 뒤에도 장기 실행 Python 프로세스가 과거 capability를 영구 캐시하는 문제를 방지하기 위해 60초 TTL 재확인을 추가했다.
- 출처 승인 상태만 있고 승인 근거가 남지 않던 공백을 `rag.source_audit_event`와 운영자 CLI로 보완했다.
- 평가 결과를 실행 단위에 묶어 평가 세트 키·버전·검색 설정이 다른 결과를 평균 비교하지 않도록 했다. 비교기는 최소 표본, 오류, recall@k, 인용 정확도, p95를 검사하지만 환경을 자동 변경하지 않는다.
- 외부 임베딩은 출처 승인과 별도로 기본 거부한다. 반출 허용 사유를 감사 이벤트로 남긴 출처만 제공자 호출을 시도하며, 적재와 저장 경계가 모두 이를 재확인한다.
- 농사로 수집기는 서비스별 API 계약을 사용하며 PDF만 추출한다. 범용 페이지 크롤링·블로그 수집은 도입하지 않았다.
- 같은 `source_version`·본문을 다시 수집할 때 고유 제약으로 실패하던 결함을 발견했다. 문서·청크를 멱등 upsert하여 기존 식별자를 보존하고, 사후에 승인된 외부 임베딩을 채울 수 있게 했다.
- `evaluation_origin`을 도입해 자동 생성 질의와 사람이 검토한 질의를 구분했다. 자동 생성 질의는 회귀 감시용 `AUTO_GENERATED` 실버 세트이며, 사용자 품질의 정답 근거로 승격하지 않는다.

## 자동 실버 평가 결과

- 승인·반출 허용된 농사로 최신 주간농사정보의 현재 청크 9개에서 LLM이 근거 문장에만 답할 수 있는 한국어 질의를 청크당 5개씩 만들었다. 총 45개는 `nongsaro-weekly-silver` / `2026-07-29-vector-silver-v2`로 기록했다.
- 같은 45개, 같은 벡터 문서에서 top-k=3 비교 결과 lexical/hybrid의 recall@k는 모두 `0.93333`이었다. hybrid의 인용 정확도는 `0.37037 → 0.31111`, p95는 `5.8ms → 397.0ms`였다.
- top-k=5에서도 recall@k는 모두 `0.97778`이었고, hybrid의 인용 정확도는 `0.28481 → 0.19556`, p95는 `4.8ms → 389.8ms`였다.
- 두 비교 실행은 모두 `NOT_READY`였다. 즉 이 작은 단일 문서 코퍼스에서는 벡터/RRF가 회수율 이득 없이 외부 임베딩 지연과 추가 후보를 만들었다. 기본값을 lexical로 유지하고 hybrid를 자동 활성화하지 않았다.

## Agent 신뢰 경계 보강

### 왜 보강했는가

- 엄격한 Responses 기반 Agent가 실패했을 때, 기존 `LocalChatWorkflow`가 별도 Chat Completions 호출로 재진입할 수 있었다. 이 경로는 Agent의 claim·citation 검증을 통과하지 않으므로 실패 후 더 약한 신뢰 경계로 우회하는 구조였다.
- `FactPackage`의 질문·대화 이력에는 제한이 있었지만, Spring 내부 호출의 `userScope`·`context`·`facts`·`sources`에는 모델 입력 전체 예산이 없었다.
- 모델의 JSON schema 준수만으로는 사람이 읽기 좋은 구조와 claim-to-citation 결속을 모두 보장할 수 없었다. 이전 계약은 최종 답변과 claim을 별도 필드로 생성하게 해, 의미가 같은지 재검증해야 하는 중복 경로를 만들었다.

### 구현·회귀 검증 사실

- 레거시 `LocalChatWorkflow`(1,109줄)와 `screen_context`(176줄)를 제거했다. AI 응답을 완료할 수 없으면 별도 문장 생성 경로로 우회하지 않고 `needs_context`의 안전한 재시도 안내만 반환한다.
- 완료 답변의 모든 claim 텍스트가 최종 답변에 실제로 존재하는지 공백 정규화 후 검사한다. claim·인용 집합·도구가 반환한 인용 ID 중 하나라도 불일치하면 `needs_context`가 된다.
- Responses 출력 계약을 `answer_blocks[]`로 바꿨다. 각 사용자 표시 블록과 그 인용 ID를 한 단위로 받고, 서버가 같은 블록을 answer·claim으로 조립한다. 이로써 모델이 별도의 answer/claim 문장을 서로 다르게 생성하는 중복 계약을 없앴다.
- 모델은 `judgment`·`evidence`·`actions`라는 섹션 의미와 인용된 원문만 반환하고, 서버가 `핵심 판단`·`근거`·`지금 할 일`의 제목과 순서를 결정적으로 렌더링한다. 형식만 고치기 위한 별도 모델 재호출은 제거했다. 형식 보정은 새로운 근거를 만들지 않는 반면 추가 비용·지연·실패 지점을 만들었고, 실제 smoke에서 근거가 있는 답변을 `needs_context`로 바꾸는 역효과가 확인됐기 때문이다. 완료 여부는 표시 형식이 아니라 claim·인용 결속으로 판단한다.
- `userScope`, `context`, `facts`, `sources`에 깊이 4, 컨테이너 항목 64, 문자열 4,000자, 총 문자열 16,000자 상한을 적용했다. 예산을 넘는 요청은 모델 호출 전에 Pydantic 검증 오류(HTTP 422)로 거절된다.
- Agent 실행 실패는 원문 예외나 프롬프트를 남기지 않고 `request_id`, `stage`, `error_type`만 구조화 warning log에 기록한다. 사용자 문구는 기존 일반 오류를 유지한다.
- Agent 실행 지표에는 `pipeline_version`과 `model_name`도 저장하고 현재 실행 프로필로만 집계한다. 따라서 응답 schema·프롬프트·도구 정책이 바뀐 이전 표본을 완료율·p95에 섞지 않는다. 원문 프롬프트·답변·도구 출력은 저장하지 않는다.
- 회귀 테스트는 claim 미반영 답변 거절, 과도한 중첩 컨텍스트 거절, Agent 실패의 안전한 응답·로그, 섹션형 answer block의 결정적 조립, Nongsaro 외부 문서 URL/크기 경계, Agent 실행 집계 저장을 검증한다. 외부 API·측정 보강 뒤 최종 Python 전체 테스트는 `72 passed`다.

### Spring 경계와 일일 리포트 정리

- Spring `AssistantService`도 Python Agent 장애나 계약 위반 뒤 규칙 기반 답변을 다시 만들지 않는다. 구조화 응답의 상태·답변·출처·인용을 확인하고, 하나라도 없으면 출처 없이 `needs_context`만 반환한다. 따라서 백엔드와 Agent의 실패 의미가 같다.
- 일일 밭 리포트는 이미 검증된 `FieldGuidanceRuleEngine` 결과를 저장한다. 이를 다시 Python의 별도 `/field-guidance` LLM 호출로 서술하던 경로는 제거했다. 이 리포트는 검색 근거나 사용자 질의를 종합하는 Agent 기능이 아니므로, 모델 재작성은 새로운 근거를 더하지 않으면서 지연·비용·장애 지점만 늘렸기 때문이다.
- 이 결정은 “LLM을 쓰지 않은 기능”을 후퇴시키는 것이 아니라, 근거 합성·인용 검증이 필요한 채팅 Agent와 규칙으로 완결되는 일일 안내의 책임을 분리한 것이다.

### 로컬 실서버 확인 (2026-07-29)

- 새 Python·Spring 프로세스를 같은 `.env`로 재기동한 뒤 `/api/v1/agent/run`에 공식 농업 질의를 요청해 HTTP 200, `completed`, 출처 3개, 299자 답변, 세 섹션 순서, 번호 행동 3개를 확인했다. 단발 소요 시간은 16.4초였다.
- 같은 엔드포인트에 지역·작물·위험·행동 3개가 포함된 현재 분석 리포트를 요청해 HTTP 200, `completed`, 출처 1개, 371자 답변, 세 섹션 순서, 번호 행동 3개를 확인했다. 단발 소요 시간은 10.7초였다.
- 행동 근거가 한 개뿐인 축소 리포트는 HTTP 200이지만 `needs_context`로 종료됐다. 근거 부족을 그럴듯한 확장 답변으로 대체하지 않는 fail-closed 동작이다.
- V28 Flyway migration으로 실행 프로필 열을 적용한 뒤, 동일 공식 농업 질의를 다시 호출해 HTTP 200, `completed`, 출처 2개, 514자 답변, 세 섹션 순서, 번호 행동 3개를 확인했다. 단발 소요 시간은 10.0초였다. 이어 사용자 밭 사실이 없는 현재 수분 질문은 HTTP 200 `needs_context`, 출처 0개, 수치 없는 42자 안내로 끝났다.
- `metrics_cli --days 30`은 새 `sectioned-citations-v1`·`gpt-4o-mini` 프로필의 요청 2건을 이전 형식 보정 표본과 분리했다. 이 중 완료 1건과 내부 `agent_error` 1건은 HTTP에서 모두 안전한 상태로 정규화되는 설계를 확인하는 구조 검증용 표본이며, 완료율·p95 성능 주장 근거가 아니다.
- `/health`와 Spring `/api/health`는 모두 HTTP 200을 반환했고, 재기동 이후 두 로그에서 ERROR·예외·실패 패턴은 확인되지 않았다. 위 수치는 로컬 환경의 단발 확인이며 운영 품질·성능 지표가 아니다.

- “Function calling의 strict schema만으로 끝내지 않고, claim이 실제 응답과 인용에 결속되는지 서버에서 재검증해 근거 누락 답변을 `needs_context`로 차단했습니다.”
- “Agent 실패 시 별도 Chat Completions 경로로 우회하던 구조를 제거하고, 검증 불가 상태를 `needs_context`로 명시해 신뢰 상태를 보존했습니다.”
- “최종 답변과 claim을 따로 생성하던 계약을 인용 포함 `answer_blocks[]`로 통합했습니다. 섹션 제목·순서는 서버가 결정적으로 렌더링하고, 형식만 고치기 위한 두 번째 LLM 호출은 제거해 인용 검증과 사용자 응답의 실패 경계를 분리했습니다.”
- “Agent 실행 로그에 모델과 파이프라인 버전을 함께 남기고 현재 프로필만 집계해, 변경 전후의 완료율·p95를 섞지 않도록 측정 경계를 만들었습니다.”
- “일일 리포트의 중복 LLM 재서술을 제거해 규칙 엔진 결과를 단일 사실 원천으로 만들고, 근거 합성이 필요한 채팅 Agent에만 모델 호출을 한정했습니다.”
- “내부 API 데이터도 모델 입력으로 취급해 중첩 깊이·항목 수·문자 수 예산을 강제했습니다.”

위 문장은 코드와 로컬 테스트로 검증된 구조적 사실이다. 실제 프롬프트 인젝션 차단률, API 비용 절감률, 장애 감소율은 운영 계측 전에는 수치로 주장하지 않는다.

## 무엇을 주장할 수 있고 없는가

- 주장 가능: PostgreSQL이 검색·지식 저장의 system of record로 동작하고, 승인·인용·추적 경로가 실제로 연결됨을 검증했다. pgvector/HNSW/RRF는 제어된 smoke와 평가 경로로 확인했지만, 현재 기본 런타임은 lexical FTS이며 45개 자동 실버 질의에서 hybrid 자동 승격 기준을 충족하지 못했음을 재현 가능하게 기록했다.
- 주장 가능: 다문서 공식 코퍼스에서도 코퍼스 지문·평가 origin·실행 ID를 고정해 lexical/hybrid의 recall@k, precision@k, MRR, p95를 비교했고, 측정값이 기준을 만족하지 않을 때 자동 승격을 차단했다.
- 주장 불가: 자동 생성·단일 문서 45건을 근거로 실제 사용자 recall@k 개선, 운영 트래픽 성능, 사용자 만족도 향상을 주장할 수 없다.
- 주장 가능: 동일 평가 세트·버전에서만 비교하도록 실행 이력을 고정하고, 외부 임베딩 반출을 출처별 명시 승인으로 제한했다.
- 다음 측정: 서로 다른 작물·계절·위험 유형의 공식 문서를 추가한 뒤, 사용자 질문 또는 사람이 검토한 골드 세트와 자동 실버 세트를 분리해 비교하고, `metrics_cli` 결과와 기간·문서 버전을 함께 보관한다.
